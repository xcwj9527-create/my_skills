# 项目大纲

让项目持续遵循用户确认的目标、边界、方案和关键参数。大纲是当前准则；新信息不能在未确认时静默覆盖它。

## 大纲文件

- 每次开始实质性项目工作前，先在项目根目录查找并读取现有大纲。优先沿用已存在且承担此作用的文件；若没有，默认创建 `PROJECT_OUTLINE.md`。
- 项目根目录以当前工作区或仓库为准。不要在个人目录或其他项目中建立副本。
- 保持大纲精简，只记录仍会影响后续决策的内容。建议包含：核心方向、范围与边界、已确认的核心方案/框架、重要参数、成功标准、待确认问题。无依据的内容写为“待确认”，不要猜测。
- 区分已确认信息与待确认信息。清楚标注尚未得到用户确认的推断；不要把推断当成项目约束。

## 每次推进项目

1. 读取当前大纲，再处理会影响项目方向、范围、框架、核心方案或关键参数的工作。
2. 将新信息判断为补充、澄清或冲突。补充和澄清不改变已确认内容时，可直接更新大纲；普通细节不必逐项询问。
3. 发现冲突时，简明指出旧大纲内容与新信息，并询问是否按新信息修订。等待答复期间，不要静默选择其中一方；可继续不依赖该决定的工作。用户明确要求“把 X 改为 Y”时，视为已授权修订，无须重复确认。
4. 用户确认后，立即更新大纲，并继续工作。若新要求尚未确认，不要把它写成已确认规则。
5. 完成实质性工作前，快速对照大纲；若结果会偏离已确认内容，先向用户说明或确认方向。

## 精简与删除

- 大纲变长时先合并重复内容、缩短表述，只保留仍指导当前项目的事实和决策。
- 某项被用户确认无用，或已明确被新决定取代且不再指导工作时，从当前大纲中删除。不要为已失效条目保留冗长历史。
- 仅凭时间久远或暂时未用，不能判断内容无用；若是否仍有效会影响工作，先询问。
- 只清理大纲中的条目，不要顺带删除源文件、交付物、日志或其他项目资料。

## 项目初次建纲

先查看用户提供的信息和项目中已有的说明，再建立精简初稿。明确区分已确认内容和待确认项；如果核心方向或关键参数仍不清楚，集中提出必要问题，不要用猜测填满大纲。向用户说明大纲文件位置，并指出需要确认的项目。
